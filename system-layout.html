Why the system does not rely on model memory alone

Vocabulary

Shared language

A formal docs/THESAURUS.md defines project terms, aliases, canonical names, and relationships so agents do not improvise meanings.

State

Persistent project entities

Projects, tasks, decisions, ideas, approvals, agents, alerts and related records are stored outside the model session.

Routing

Capability-based assignment

Jobs route by what a worker can actually do, not by a hard-coded machine name or a model guessing which host should receive work.

Verification

Audit + receipts

Meaningful actions are logged, and the architecture is being extended around execution receipts so the UI never treats an unverified claim as completed work.

Guardrail design and implementation boundaries

Architect-specified facts

Core architectural facts are protected from casual mutation by non-authorized actors.

Fail-closed roles

Unknown or unset actor roles do not silently gain access.

Append-only audit

Audit and job-event history are designed to remain traceable rather than being rewritten after the fact.

Approval separation

Structural changes cannot self-approve, and client approval is not treated as architect approval.

Allowlisted handlers

Worker execution is restricted to registered handlers rather than arbitrary command strings.

Human override

External or higher-risk actions remain gated by policy and human approval.

These controls do not certify end-to-end acceptance. M3 did not exercise live approval or platform execution; v2 easy actions are constrained by permission levels and adapters, and code.edit currently has no declared undo inverse.

Vocabulary layer

Approved naming distinguishes JEV (studio-wide routing) from house-agent (the Blackland role). Legacy JEV heartbeat filenames remain; this decision does not imply every registry has migrated. Canonical definitions keep agents and developers aligned.

  • Canonical term — the one name the system stores.
  • Aliases — natural language names people may also use.
  • Type — Project, Task, Event, Client, Worker, Capability, Approval, etc.
  • Relationships — what the term may contain or reference.
  • Do-not-confuse-with — terms that sound similar but mean something different.
  • Examples — concrete project-specific usage.

Operating model

1

Observe

LMC, tools, project state, or a user action produces structured state.

2

Understand

Canonical vocabulary and active project context resolve what names and references mean.

3

Route

JEV decides whether the task belongs on a fast path, deep-reasoning path, or specific capable worker.

4

Act

Claude Code, Codex, MCP, or a registered local tool performs the bounded action.

5

Verify

The system records result state and activity instead of trusting a generated statement that work was completed.

6

Remember

Reusable terms, decisions, project state and proven workflows are persisted for later sessions.
